# HTTP API

Everything `atlas-server` exposes over HTTP. Sixteen routes across four
prefixes, plus a health check at the root.

Two different credentials gate this surface, and mixing them up is the
most common first mistake:

| Prefix | Credential | Who it represents |
|---|---|---|
| `/api/mcp` | `ATLAS_MCP_TOKEN`, one shared bearer | an **agent** |
| `/api/auth`, `/api/sync`, `/api/afg` | a session token from `/api/auth/login` | a **person** |
| `/health` | none | anyone |

An agent bearer will not open a sync stream, and a person's session
token will not call an MCP tool. That separation is deliberate: the MCP
token is shared by every agent on the machine and identifies nobody,
which is exactly what you do not want deciding whose personal data a
request may read.

Every error response carries the same envelope:

```json
{ "error": "a human-readable sentence" }
```

`401` responses also carry `WWW-Authenticate: Bearer`, so a client can
tell "you are not authenticated" from "you are, and may not do this"
without parsing prose.

## Health

### `GET /health`

No authentication. Runs a real query against the database rather than
answering as soon as the process is up — a health check that returns
`ok` while its storage is unreachable is decoration.

```json
{ "status": "ok", "version": "0.1.0" }
```

Returns `503` with `{ "status": "degraded", "reason": "db unavailable" }`
when that query fails.

## Authentication — `/api/auth`

A `user` object appears in several responses and always has this shape:

```json
{
  "id": "01M1TD4YJR7X1JTK29NTBB1AD3",
  "email": "dev@example.com",
  "display_name": "Dev",
  "created_at": "2026-09-06T03:45:46.072907314Z",
  "updated_at": "2026-09-06T03:45:46.072907314Z",
  "must_change_password": false
}
```

A `session` response wraps it:

```json
{
  "token": "b0d663ad634de43ae2fb26aee911bf07…",
  "expires_at": "2026-10-06T03:45:46.078288771Z",
  "user": { }
}
```

`token` is returned exactly once, at creation. Only its hash is
persisted, so a lost token is replaced by logging in again rather than
recovered.

### `POST /api/auth/register`

Bootstraps the **first and only** account. Every later call fails —
this is not a signup endpoint, and there is no public registration
surface — the server is yours. Additional accounts arrive by invitation.

```json
{ "email": "dev@example.com", "password": "correct horse battery", "display_name": "Dev" }
```

| Status | When |
|---|---|
| `201` | account created; body is a session |
| `400` | email has no `@`, or password under 8 characters |
| `403` | an account already exists |

### `POST /api/auth/login`

```json
{ "email": "dev@example.com", "password": "correct horse battery" }
```

`200` with a session, or `401`. A wrong password, an unknown email and
a disabled account all return the **same** body, byte for byte — the
caller must not learn which one it was. The unknown-email path runs a
hash verification against a dummy value so it takes about as long as a
real one, closing the timing side channel too.

### `GET /api/auth/me`

Bearer required. Returns the `user` object. This route and
`change-password` are the only two an account with
`must_change_password` set may reach.

### `POST /api/auth/invite`

Bearer required. Creates an account for someone else. There is no admin
role — the server is single-tenant — so any authenticated session may
invite.

```json
{ "email": "teammate@example.com", "display_name": "Teammate" }
```

```json
{
  "user": { "must_change_password": true },
  "temporary_password": "8f2c…"
}
```

The password is **generated by the server, never chosen by the
inviter** — so the inviter relays a one-time value and never learns the
credential the account ends up using. Like a session token it is
returned exactly once.

| Status | When |
|---|---|
| `201` | account created |
| `401` | no or invalid bearer |
| `403` | the caller has not yet replaced their own temporary password |
| `409` | that email already has an account |

### `POST /api/auth/change-password`

Bearer required, and exempt from the `must_change_password` block — an
invited account needs precisely this route to stop being restricted.

```json
{ "current_password": "8f2c…", "new_password": "a settled password" }
```

`204` on success. The current password is re-verified even though the
caller already holds a valid session, so a leaked bearer alone cannot
take over an account by rotating its password.

### `POST /api/auth/users/{id}/disable`

Bearer required. A disabled account loses access through **every** path
— password login, GitLab login, and any session token issued before it
was disabled. Existing tokens are not deleted; they simply stop
resolving.

| Status | When |
|---|---|
| `204` | disabled |
| `400` | the target is the caller's own account |
| `404` | no such user |

Disabling yourself is refused because it would lock out the only
session that could undo it.

### `POST /api/auth/users/{id}/enable`

Bearer required. `204`, or `404` if no such user.

### `GET /api/auth/oauth/gitlab/start`

**Only mounted when GitLab OAuth is configured.** With the four
`ATLAS_OAUTH_*` variables unset these two routes do not exist at all —
they return `404` rather than a "not configured" error, so a Mode 1
install has nothing extra to probe.

Responds `303` to GitLab's authorize endpoint, carrying a signed
`state`.

### `GET /api/auth/oauth/gitlab/callback?code=…&state=…`

Verifies `state` **before** any network call, exchanges the code, reads
the GitLab profile, and resolves it to an existing Atlas account.

It never creates one. Resolution is: an already-linked GitLab identity,
or an existing account with a matching email. If neither matches — or
the account that matches is disabled — the request is refused with the
same error in all three cases, so probing this endpoint reveals nothing
about which accounts exist.

| Status | When |
|---|---|
| `200` | a session, same shape as `/login` |
| `400` | `state` missing, malformed, expired (5 minutes) or wrongly signed |
| `403` | no local account is linked to that GitLab identity |
| `503` | GitLab was unreachable or rejected the exchange |

## Sync — `/api/sync`

The server side of the three propagation modes — see
[Sync](/concepts/sync). Every route
takes a **person's** session token, not the MCP bearer: a sync client
acts as a specific human, and `owner_id` is taken from that identity
rather than from the request body.

### `POST /api/sync/sessions/push`

```json
{ "sessions": [ { "id": "01M1T52M…", "project": "your-org/your-project", "…": "…" } ] }
```

Returns `{ "sessions": [ … ] }` — the authoritative rows after
last-write-wins by `updated_at`. Each incoming row is stored under the
authenticated owner; a row claiming a different owner is a `409`.

### `GET /api/sync/sessions/pull?since=`

`since` is optional and RFC 3339; omitted, it returns everything.
Returns only the caller's own sessions.

### `POST /api/sync/memory/push`

Carries both memory buckets in one payload, routed by each entry's own
`scope` — see [State and privacy](/concepts/state-and-privacy):

```json
{
  "entries": [
    { "scope": "project",  "project": "your-org/your-project", "key": "build", "value": "cargo build --release", "…": "…" },
    { "scope": "personal", "owner_id": "01M1TD4…",       "key": "diary", "value": "mine alone",            "…": "…" }
  ]
}
```

Project entries (Type 1) go through as-is. Personal entries (Type 2) are
forced under the caller's own owner id and the incoming `owner_id` is
**ignored outright** — a client that lies writes into its own bucket
rather than being refused, so no path here touches another developer's
memory.

Last-write-wins keys on `(project, key)` or `(owner_id, key)`, not on
the row id: two machines can remember the same fact without having seen
each other's row, so they hold different ids for it.

### `GET /api/sync/memory/pull?since=`

Returns all project memory plus the caller's own personal memory, and
never anyone else's.

### `POST /api/sync/notes/push`

Applies notes arriving from another machine. Notes are Type 2
throughout, so unlike memory there is no bucket to route between:
**every note is stored under the authenticated caller**, never the
owner the row claims.

A client that claims another owner is not refused — it simply writes
into its own notes, because there is no path here that touches a
different developer's.

```json
{ "notes": [ { "id": "…", "name": "scratchpad", "body": "…",
               "created_at": "…", "updated_at": "…" } ] }
```

Last-write-wins on `updated_at`, compared against the note with the
same **name** rather than the same id: two machines that wrote the same
note independently produced different ids for what the developer
considers one note.

### `GET /api/sync/notes/pull?since=`

Returns the caller's own notes and nobody else's. `since` is a
timestamp cursor and is **strictly after**, so a poll loop does not
re-deliver what it just saw.

### `GET /api/sync/events`

The `live`-mode stream. `text/event-stream`, held open, with
a keep-alive comment every 15 seconds so an idle connection survives
proxies.

```
event: change
data: sessions

event: change
data: memory

event: change
data: notes
```

The event is a **notification, not state**: it names what kind of thing
changed, and the client answers with the same pull it would have run on
a timer. That keeps one consistency path rather than two, and makes a
missed event harmless — the pull that follows collects everything.

Only events for the authenticated caller's own data are delivered.
Another developer's push never appears on this stream.

## Workflow runs — `/api/afg`

### `GET /api/afg/runs/{run_id}/events`

A run's timeline, live. `text/event-stream`, keep-alive every 15
seconds.

Unlike the sync stream, **these events carry their full payload**
— workflow node events are append-only and immutable, so
there is no second consistency path to create, and a viewer forced to
re-fetch the whole run per event would make fifty requests for a
fifty-event run.

```
event: enter
data: {"id":"01M1T7PY7C…","run_id":"01M1T7PY79…","node_id":"build","kind":"enter",
       "payload":{"title":"Build","isRetry":false},"message_id":null,
       "at":"2026-09-06T02:10:44.076683908Z"}
```

The SSE event name is the node event's kind — one of `enter`, `exec`,
`gate_pass`, `gate_fail`, `retry`, `advance`, `complete`, `error`.

Three behaviours worth knowing:

- **History and live share one connection.** On connect the stream
  replays the run's existing events, then continues with new ones. A
  watcher joining a run in progress sees the whole timeline without a
  second request. The subscription opens before history is read and
  replayed ids are skipped when they arrive live, so an event landing
  in that window is delivered exactly once.
- **The stream closes itself** once the run reaches `complete` or
  `error`, rather than hanging open on a run that will never move
  again. Watching a finished run therefore returns its timeline and
  disconnects.
- **A watcher that falls behind is told so** with an
  `event: lagged` carrying `{"missed": n}`. Unlike a sync
  notification there is no later pull to repair a hole, so the gap is
  reported rather than left to be rendered as a complete run.

A run belongs to the owner of its initiating session. Anyone else gets
`404`, not `403` — the endpoint never confirms that a run they cannot
see exists.

## Webhooks — `/api/webhooks/tracker`

Mounted only when `ATLAS_TRACKER_WEBHOOK_SECRET` is set. Without it
every route below is `404` — an unauthenticated receiver would let
anyone make this server fetch from the tracker on its own credentials.

### `POST /api/webhooks/tracker/gitlab`

Receives GitLab's *Issues events* and refreshes the one issue the event
names. Register it in GitLab under **Settings → Webhooks**, over HTTPS,
with the *Secret token* set to `ATLAS_TRACKER_WEBHOOK_SECRET`.

Authenticated by the `X-Gitlab-Token` header, compared in constant time
through a digest so a wrong length is rejected without the comparison
revealing it.

| Situation | Response |
|---|---|
| Token missing or wrong | `401`, and nothing is read or stored |
| An issue event | `200 {"scheduled":1}` |
| Any other event, or a body this cannot read | `200 {"scheduled":0}` |

Two things about that table are deliberate:

- **An event it does not handle is a success.** A non-2xx teaches
  GitLab to disable the hook, and there is nothing wrong on the
  tracker's side.
- **The response does not wait on the refresh.** GitLab disables a hook
  that times out, so the fetch runs off the response path and its
  failures are logged. A missed refresh is caught by the polling loop,
  which is why that loop stays.

**Nothing from the payload is stored.** GitLab's token echo proves the
sender knew a secret; it is not a signature over the body, so the
payload is used only to learn *which* issue to ask about, and
everything written comes from an authenticated call back to the
tracker. A forged body can at worst cause a wasted fetch.

## MCP — `/api/mcp`

### `POST /api/mcp`

JSON-RPC 2.0 over HTTP, protocol `2025-06-18`. Authenticated with
`ATLAS_MCP_TOKEN` as a bearer, compared in constant time.

Methods: `initialize`, `tools/list`, `tools/call`. The 31 tools are
listed in [MCP tools](/reference/mcp-tools); for pointing a real agent
CLI at this endpoint see
[Connecting an agent](/guide/connecting-agents).

```bash
curl -X POST http://127.0.0.1:4000/api/mcp \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $ATLAS_MCP_TOKEN" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

A tool that fails returns a JSON-RPC `error`, not an HTTP error status
— the transport succeeded. Codes below `-32000` are the standard
JSON-RPC set; `-32000` and downward are Atlas's own:

| Code | Meaning |
|---|---|
| `-32000` | tracker: not found |
| `-32001` | tracker: unauthorized |
| `-32002` | tracker: rate limited |
| `-32003` | tracker: disabled (no tracker configured) |
| `-32004` | tracker: invalid request |
| `-32005` | tracker: conflict |
| `-32006` | session not found |
| `-32007` | terminal not running |
| `-32008` | terminal: path not found on this machine |
| `-32009` | workflow or run not found |
| `-32010` | terminal: git credentials missing for a restore |
| `-32011` | memory: no value under that key |
