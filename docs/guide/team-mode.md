# Team mode

A team server is another `atlas-server` — the same binary, the same
image — that your machines sync against. It holds no privileged
position beyond being the one everyone can reach.

Reach for it when a second machine or a second person shows up. Nothing
you built in Mode 1 needs redoing: existing sessions replicate as they
are.

This page is about **access** — accounts, invitations, what replicates
and what stays private. It is not how a team agrees on the way it
works: that travels in the repository rather than through the server,
and is covered in
[A shared way of working](/guide/shared-way-of-working).

## Stand it up

Deploy the image somewhere both machines can reach
([Deployment](/guide/deployment)), then create the first account:

```bash
curl -X POST https://atlas.example.com/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"a long passphrase","display_name":"You"}'
```

```json
{ "token": "b0d663ad…", "expires_at": "2026-10-06T…", "user": { "id": "01M1TD4…" } }
```

Keep both values — the `token` is your bearer for every sync call, and
the `id` is your `owner_id`. The token is returned exactly once; only
its hash is stored, so a lost one is replaced by logging in again.

**`register` works once.** Every later call is refused. This is not a
signup endpoint and there is no public registration surface — the
server is yours, and additional accounts arrive by invitation.

## Add a teammate

```bash
curl -X POST https://atlas.example.com/api/auth/invite \
  -H "Authorization: Bearer $YOUR_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"email":"teammate@example.com","display_name":"Teammate"}'
```

```json
{ "user": { "id": "01M1TD5…", "must_change_password": true },
  "temporary_password": "8f2c…" }
```

The password is **generated by the server, never chosen by you** — so
you relay a one-time value and never learn the credential they end up
using. Like a session token, it is shown exactly once.

Until they replace it with `POST /api/auth/change-password`, their
account can reach only `/me` and that route. An unenforced "you should
change this" flag would be decoration; the point of a temporary
password is that it stops working.

There is no admin role. The server is single-tenant, so any
authenticated session can invite, disable or enable another account.

## Removing access

```bash
curl -X POST https://atlas.example.com/api/auth/users/$USER_ID/disable \
  -H "Authorization: Bearer $YOUR_TOKEN"
```

A disabled account loses access through **every** path at once —
password login, GitLab login, and any session token issued before it
was disabled. Existing tokens are not deleted; they simply stop
resolving, which is why there is no window between disabling someone
and their last session expiring.

You cannot disable your own account: it would lock out the only session
that could undo it.

## Sync your machines

```jsonc
// sync.sessions_now — one pass, right now
{ "remote_url": "https://atlas.example.com/api/sync/",
  "bearer_token": "b0d663ad…",
  "owner_id": "01M1TD4…" }

// sync.memory_now — same, for agent memory
```

Note the trailing slash on `remote_url`, and that the bearer is the
token that **server** issued, not your local `ATLAS_MCP_TOKEN`. They
are different credentials for different things: one identifies a
person, the other identifies nothing and is shared by every agent on
the machine.

Then pick a cadence:

```jsonc
// sync.set_mode
{ "mode": "live", "remote_url": "…", "bearer_token": "…", "owner_id": "…" }
{ "mode": "auto", "interval_secs": 60, "remote_url": "…", … }
{ "mode": "focus" }
```

`focus` is the default and stops any running loop. `auto` polls.
`live` holds a stream open and syncs the moment the server reports a
change, reconnecting on its own if it drops. Your teammate can be in a
different mode than you without either of you noticing —
see [Sync](/concepts/sync).

```jsonc
// sync.status
{ "mode": "live", "stream_connected": true,
  "last_report": { "pushed": 2, "pulled": 1 }, "last_error": null }
```

`stream_connected` is worth checking in `live`: a long-lived connection
that dies silently otherwise looks exactly like a quiet team.

::: warning Re-arm after a restart
The remote URL and bearer live in process memory only and are never
written to disk. A restart drops back to `focus`. That is deliberate —
the alternative is a file holding a credential for another machine.
:::

## What replicates, and what stays yours

Sessions and agent memory today.

**Project state is shared.** Project-scoped agent memory reaches
everyone on the project — that is what makes it worth having.

**Personal state is not.** It replicates so your second laptop has it
and a dead disk does not lose it, and it is stored marked private to
you: no admin view, no reporting query that includes it. A client that
pushes a row claiming a different owner has it filed under **its own**
owner instead, so there is no path that writes into someone else's
data at all.

Details in [State and privacy](/concepts/state-and-privacy).

## Continue with GitLab

If the server is configured for it, teammates can log in with GitLab
instead of a password. It **links** to an existing account — matching a
previously linked identity, or an account with the same email — and
never creates one. Somebody with a GitLab account and your server's URL
does not thereby get in.

Configuration is four variables, all or none:
[Environment variables](/reference/environment#gitlab-oauth).
